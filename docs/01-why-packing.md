# 为什么必须打包？—— 一次真实的失败

## 症状

第一次做全量备份（约 2500 个文件 / 1.6 GB），用 rclone 直传：

```
21:02:45  开始上传
21:06:16  163 MiB / 1.635 GiB, 10%, 776 KiB/s, ETA 33m
21:10:16  265 MiB / 1.635 GiB, 16%, 1.463 KiB/s, ETA 1w4d9h     ← 开始异常
21:14:54  最后一次成功复制
21:17:16  273 MiB / 1.635 GiB, 16%, 10 B/s                      ← 衰减
21:20:16  273 MiB / 1.635 GiB, 16%, 0 B/s, ETA -                ← 完全停滞
```

**迷惑人的地方：**

- rclone **进程还活着**，没有报错
- 速度是**平滑衰减**的（不是突然断掉），看起来像网络抖动
- 传输量冻结，但文件计数也在冻结

## 排查

1. 查进程 → 活着，CPU 很低
2. 查 TCP 连接 → **没有任何到坚果云的连接**
3. 单独发一个请求验证：

```
ERROR: error listing: couldn't list files:
Too many requests are received recently: BlockedTemporarily: 503 Service Unavailable
```

**真相：不是网速问题，是请求数超了配额。**

## 根因

坚果云 WebDAV 的限制：

| | |
|---|---|
| 免费版 | 600 次请求 / 30 分钟 |
| 付费版 | **1500 次请求 / 30 分钟** |

而上传一个文件需要 3~4 次请求（检查存在性 + PUT + 确认）。
2500 个文件 ≈ **1 万次请求** → 远超配额 → 被封禁。

## 解法

**先打包，再上传。**

| | 打包前 | 打包后 |
|---|---|---|
| 文件数 | 2554 | **4** |
| 请求数 | ~10000 | **~20** |
| 体积 | 1635 MB | **838 MB** |

- 请求数下降 **500 倍**
- 体积下降近一半（JSONL 文本压缩率极高）
- 打包后单次上传 6 分钟完成

## 两个附带注意事项

**① 压缩包必须按「未压缩体积」分卷**
否则可能出现"压缩后仍超过网盘单文件上限"的情况。
坚果云单文件上限 500 MB，所以默认按 450 MB 分卷。

**② 限流解除需要等窗口过期**
被封后**不要反复试探**——每次试探也算请求，可能延长封禁。
等 30 分钟后一次性完成。

## 什么时候不需要打包？

如果你用的是**对象存储**（S3 / Cloudflare R2 / Backblaze B2），
通常**没有请求频率限制**（按请求数计费，很便宜），可以直接传。
打包主要是为了对付 WebDAV 类网盘。
